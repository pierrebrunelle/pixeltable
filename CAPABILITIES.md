# Python API parity and release evidence

This is a capability inventory, not a claim of full Python SDK parity. The catalog adapter executes against Python; it does not embed the Pixeltable engine in JavaScript. The HTTP client calls application-defined routes, while `./experimental/catalog` uses the internal versioned proxy protocol.

Audited against the Python public exports in `pixeltable/__init__.py`, table methods in `pixeltable/catalog/table.py`, and query methods in `pixeltable/_query_base.py` and `pixeltable/_query.py`. The current Python base is upstream commit `b49ca12607d7c96e6940cc103f3b9eabd817711e`; the SDK includes a serving-metadata addition. Protocol version 4 and metadata schema version 56 are required. Re-audit when these sources change.

“Implemented” below means the stated subset exists and has the cited local test coverage. “Partial” means a related API exists but does not cover Python's full behavior. “Missing” means there is no dedicated SDK operation. These labels do not imply that GitHub CI or a hosted deployment has passed. Evidence links resolve in the source checkout; test files are intentionally excluded from the npm package.

## Next acceptance work

1. Extend two-source joins to chained joins and aliases, preserving scope isolation, outer nullability, and Python serialization.
2. Extend inline binary support to catalog array/media representations with transport round trips and Python-equivalent computed pipelines.
3. Add projected/iterator views and the remaining schema operations, followed by a concrete schema-diff/preview contract.
4. Complete the authenticated application with a real session provider and shared job store; test the full browser flow.
5. Establish repository/package ownership, hosted integration, version support policy, and verified release CI.

The remaining rows above stay open even when the current test suite passes. New capabilities should update this inventory, add Python contract and live tests, and state any narrower behavior explicitly.
